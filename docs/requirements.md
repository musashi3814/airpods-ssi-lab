# サイレントスピーチに必要なデータ要件

AirPods でサイレントスピーチ(SSI: Silent Speech Interface)を作るには、どんな信号が、どの品質で必要か。各要件を AirPods のどの経路で取れそうか、どの実験で確かめるかを一覧にした。アプリ(`ios/`)と解析スクリプトは、ここで定める要件 ID (R1〜R13, L1〜L4) をキーにして判定を出す。

## 1. 方式ごとに必要な信号

| 方式 | 代表研究 | 計測するもの | 必要な信号 |
|---|---|---|---|
| **A. アクティブ音響** | ReHEarSSE (CHI'24), HEar-ID (UbiComp'25), HPSpeech (ISWC'23) | 口や顎の動きによる耳道の変形を、既知プローブ音の反射の変化として捉える | スピーカーから非可聴プローブ (17.5〜23 kHz) を出し、耳道内のマイクで同時録音する |
| **B. パッシブ音響** | ささやき認識、NAM マイク | ささやき声・呼気・舌打ちなど、微弱だが音として出るもの | 帯域 8〜11 kHz 以上のマイクで、ノイズ抑圧がかかっていないもの |
| **C. IMU** | MorsEar (CHI'26), mousepods, Subvox | 顎・頬の動きが伝わったイヤホンの微小な揺れ | 加速度・角速度。顎の動きは概ね 15 Hz 以下なので、50〜100 Hz 以上で連続して届けばよい |

HEar-ID は A と B を併用している(OFDM 反射 + ささやき音)。

## 2. 要件一覧

状態の見方: ✅ 既知の事実で満たす / ❌ 満たさないことが既知 / ❓ 未測定(実験で決める)

### A. アクティブ音響

| ID | 要件 | 閾値の目安 | 理由 | iOS 公開 API | Linux 非公開経路 (0x58) | 確認する実験 |
|---|---|---|---|---|---|---|
| R1 | マイクのサンプリング周波数 | ≥ 47 kHz | 23 kHz まで表現するため(23 kHz < 0.49·fs) | ❓(HFP は 16/24 kHz で ❌。高品質録音モードの実レートは不明) | ✅ 64 kHz | E1 / L4 |
| R2 | マイク経路が 17.5〜23 kHz を通す | プローブ帯の SNR > 10 dB | エンコーダの低域通過で消えることがある | ❓ | ❓ | E2 / L4 |
| R3 | スピーカー出力が 17.5〜23 kHz を出す | 同上 | A2DP の AAC エンコーダが高域を切る可能性 | ❓ | ❓ | E2b / L4 |
| R4 | 再生したプローブがエコーキャンセラで消されない | 整合フィルタのピーク/中央値 > 10 | 通話系 DSP は自分の再生音を除去する | ❓ | ❓(通話モード扱い) | E2 / L4 |
| R5 | 再生→録音の遅延が安定し、サンプルが欠落しない | フレームごとの遅延の標準偏差 < 0.1 ms、ドリフトを推定できる | 反射の遅延差 (~0.1 ms) を見るため | ❓ | ❓(ジッタ p95 55 ms。ただしパケット単位) | E2 / L4 |
| R6 | マイクが耳道内の音を拾う(内向き / 閉塞側) | ANC オン/オフで外来音が 10 dB 以上変わる | 耳道の反射を拾うには耳の内側のマイクが要る | ❓(通話用の外向きマイクの可能性が高い) | ❓ | E3 / L1 / L2 |

### B. パッシブ音響

| ID | 要件 | 閾値の目安 | 理由 | iOS | Linux | 実験 |
|---|---|---|---|---|---|---|
| R7 | 帯域 ≥ 8 kHz で、ささやきが抑圧されない | ささやき区間の 2〜8 kHz SNR > 10 dB | ノイズ抑圧はささやきを雑音として消す | ❓ | ❓ | E1 / E3 |

### C. IMU

| ID | 要件 | 閾値の目安 | 理由 | iOS | Linux | 実験 |
|---|---|---|---|---|---|---|
| R8 | IMU のレート | ≥ 50 Hz | 顎の動き (~15 Hz) を折り返しなく捉える | ❌ ~25 Hz(既知) | ✅ ~100 Hz(Pro 2/3) | E4 |
| R9 | 静止時も途切れずに届く | 200 ms 以上のギャップ ≒ 0 | 動き出しを捉えるため | ❓(Linux では静止中は送られない報告あり) | ❓ | E4 |
| R10 | 口の動きが IMU に現れる | 口パク時 / 安静時のエネルギー比 > 3 dB | 頭の揺れに埋もれないこと | ❓ | ❓ | E4 |

### 共通: 「単語の情報があるか」

| ID | 要件 | 閾値の目安 | 理由 | 実験 |
|---|---|---|---|---|
| R11a | IMU だけで単語を区別できる | LOO 1-NN 精度 > チャンス、置換検定 p < 0.05 | 情報の有無そのものを見る | E5 |
| R11b | パッシブ音だけで区別できる | 同上 | | E5 |
| R11c | アクティブ反射だけで区別できる | 同上 | | E5 |
| R12 | 音声と IMU の時刻を同期できる | ≤ 10 ms | マルチモーダル融合のため | E5(同一のホストクロックで記録) |
| R13 | 装着し直しても再現する | 装着し直し後の精度低下が小さい | 製品として成立する条件 | E5 を装着し直して 2 回実行 |

### 非公開経路(Mac / Linux でしか確かめられないもの)

| ID | 問い | 実験 |
|---|---|---|
| L1 | イヤーチップ装着状態テスト中に、イヤホン→ホストへ音声ストリーム(内向きマイク)が流れるか | `mac/` のキャプチャ手順 + `aacp_capture_summary.py` |
| L2 | ライブ翻訳時に、通話時と違うマイク構成(0x58 START ペイロード)が使われるか | 同上 |
| L3 | SensorDataWX の SPL0 サービス (17) から何が届くか | `linux/aap_lab.py sensor --service 17` |
| L4 | 0x58 経路(64 kHz)で R2〜R5 を満たすか。モードバイトを変えると R6 が変わるか | `linux/aap_lab.py mic` / `fuzz-mode` + `analysis/probe.py` |

## 3. 判定の流れ

```
E1 (経路・形式) ─┬─ fs ≥ 47k の構成がある ─→ E2 (プローブ行列) ─┬─ R2/R4 OK ─→ E3 (マイク位置) ─→ E5 (active)
                 │                                              └─ NG ─→ iOS ではアクティブ音響不可 → L4 (Linux) で再判定
                 └─ なし ─→ iOS ではアクティブ音響不可
E4 (IMU) ─→ R10 OK ─→ E5 (IMU)
E5 ─→ 方式ごとの「情報あり / なし」を確定
```

- **iOS で全部 NG の場合**: 「iOS 公開 API では SSI に必要な信号が取れない」と結論してよい。その場合、残る道は Linux / Android の非公開経路 (L1〜L4)、または別ハードウェア。
- **E5 で R11a だけ OK の場合**: 少語彙のコマンド入力(IMU 方式)なら iOS アプリとして製品化を検討できる。
